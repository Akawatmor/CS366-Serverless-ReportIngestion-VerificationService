
รายงานผล
ส่วนที่ 1 ที่มาของโครงงาน
ที่มาและความสำคัญของปัญหา
ในสถานการณ์ภัยพิบัติ ข้อมูลรายงานเหตุการณ์จากภาคประชาชนนับเป็นปัจจัยสำคัญต่อการตอบสนองและให้ความช่วยเหลือของหน่วยงานที่เกี่ยวข้อง โดยในปัจจุบันประชาชนสามารถรายงานเหตุการณ์ผ่านช่องทางที่หลากหลาย เช่น สื่อสังคมออนไลน์ แอปพลิเคชันบนสมาร์ทโฟน และเซนเซอร์อุปกรณ์ IoT (Internet of Things) อย่างไรก็ตาม ความหลากหลายของช่องทางและปริมาณข้อมูลก่อให้เกิดปัญหาหลัก 3 ประการ ได้แก่ ภาวะข้อมูลมหาศาล เมื่อเกิดภัยพิบัติ ปริมาณรายงานจะหลั่งไหลเข้ามาสู่ระบบพร้อมกันในปริมาณมาก ทำให้เจ้าหน้าที่ไม่สามารถคัดกรองข้อมูลได้ทันท่วงที ความซ้ำซ้อนของข้อมูล จากการที่ประชาชนหลายรายรายงานเหตุการณ์เดียวกันจากพื้นที่เดียวกัน ทำให้เกิดความสับสนและสิ้นเปลืองทรัพยากรในการประมวลผล และโครงสร้างข้อมูลที่ไม่เป็นมาตรฐาน เนื่องจากข้อมูลที่มาจากหลากหลายแหล่งที่มาขาดรูปแบบที่ชัดเจน ทำให้ยากต่อการนำไปประมวลผลร่วมกัน
ด้วยเหตุทั้งหมดนี้ โครงงานนี้จึงมุ่งเน้นพัฒนาระบบรับและตรวจสอบรายงานภัยพิบัติ ที่สามารถรวบรวมข้อมูลจากแหล่งต่าง ๆ มาแปลงให้อยู่ในรูปแบบมาตรฐานเดียวกัน พร้อมทั้งประยุกต์ใช้ปัญญาประดิษฐ์ในการวิเคราะห์ คัดกรองข้อมูลที่ซ้ำซ้อน และส่งต่อให้เจ้าหน้าที่ยืนยันความถูกต้องก่อนประกาศเป็นเหตุการณ์จริง
วัตถุประสงค์ของโครงงาน
•	เพื่อพัฒนาระบบรับรายงานสถานการณ์ภัยพิบัติที่สามารถรองรับการหลั่งไหลของปริมาณข้อมูลมหาศาลในช่วงเวลาวิกฤตได้อย่างมีประสิทธิภาพ
•	เพื่อประยุกต์ใช้เทคโนโลยีปัญญาประดิษฐ์ชนิดโมเดลทางภาษาขนาดใหญ่ในการวิเคราะห์ประเมินความน่าเชื่อถือของรายงานที่ได้รับ
•	เพื่อออกแบบและพัฒนาระบบอัลกอริทึมตรวจจับข้อมูลซ้ำซ้อนโดยอาศัยการคำนวณระยะทางทางภูมิศาสตร์ และข้อมูลเหตุการณ์ที่เกิดขึ้นก่อนหน้า

•	เพื่อศึกษาและทดลองออกแบบสถาปัตยกรรมระบบแบบไร้เซิร์ฟเวอร์ (Serverless Architecture) บนแพลตฟอร์มคลาวด์ AWS
ขอบเขตของการพัฒนา
ในขอบเขตด้านระบบ โครงงานนี้มุ่งเน้นการพัฒนาเฉพาะโมดูลระบบรับและตรวจสอบรายงานภัยพิบัติเบื้องต้นเท่านั้น ไม่ครอบคลุมถึงระบบการติดตามเหตุการณ์ที่เกิดขึ้นแล้ว หรือระบบการแจ้งเตือนภัยไปยังประชาชน
ในขอบเขตด้านข้อมูล โครงงานนี้ใช้ชุดข้อมูลจำลองในการทดสอบการทำงานของระบบ
ในขอบเขตด้านเทคโนโลยี โครงงานนี้ โปรแกรมประมวลผลต้นฉบับพัฒนาระบบด้วยภาษา Python และจัดการโครงสร้างพื้นฐานด้วย Terraform โดยใช้บริการของ AWS เป็นหลัก
ประโยชน์ที่คาดว่าจะได้รับ
ในเชิงปฏิบัติการ คาดว่าจะได้ระบบต้นแบบที่สามารถประมวลผลข้อมูลรายงานภัยพิบัติได้อย่างรวดเร็ว ช่วยลดภาระการทำงานของเจ้าหน้าที่ และมีสถาปัตยกรรมที่สามารถขยายตัวรองรับการใช้งานอัตโนมัติซึ่งช่วยประหยัดงบประมาณแต่มีประสิทธิภาพสูง
ในเชิงวิชาการและทักษะ คาดว่าผู้พัฒนามีความรู้ความเข้าใจในการออกแบบสถาปัตยกรรมแบบ Event-Driven เข้าใจกลไกการทำงานร่วมกันของบริการคลาวด์ AWS ได้แก่ Lambda DynamoDB SQS และ EventBridge และสามารถบูรณาการเทคโนโลยี Generative AI เข้ากับระบบงานจริงได้

ส่วนที่ 2 รายงานผลลัพธ์การดำเนินงาน
วิธีการและขั้นตอนการพัฒนาระบบ
การพัฒนาระบบรับและตรวจสอบรายงานภัยพิบัติอาศัยแนวคิดการออกแบบสถาปัตยกรรมแบบไร้เซิร์ฟเวอร์ และการขับเคลื่อนด้วยเหตุการณ์บนแพลตฟอร์ม Amazon Web Services (AWS) โดยมีขั้นตอนและกลไกการทำงานแบ่งออกเป็น 4 กระบวนการหลัก ได้แก่
•	กระบวนการรับข้อมูล ระบบได้รับการออกแบบให้รองรับปริมาณการเรียกใช้งานบริการนำเข้าข้อมูลจำนวนมากในช่วงเวลาที่เกิดวิกฤต โดยใช้ Amazon API Gateway เป็นจุดรับคำขอผ่านโปรโตคอล REST API เพื่อความปลอดภัยและป้องกันการโจมตี ระบบได้บูรณาการร่วมกับการตรวจสอบสิทธิ์ด้วย API Key และกำหนดนโยบายจำกัดอัตราการเรียกใช้งานไว้ที่ 50 คำขอต่อวินาที ข้อมูลที่ผ่านเกณฑ์จะถูกส่งต่อไปยังบริการ Amazon SQS (Simple Queue Service) ซึ่งทำหน้าที่เป็นคิวพักข้อมูลชั่วคราว เพื่อป้องกันสภาวะคอขวดหากมีข้อมูลนำเข้าจำนวนมากในเวลาฉับพลัน
•	กระบวนการประมวลผลและวิเคราะห์ความน่าเชื่อถือ ระบบให้บริการ AWS Lambda ทำหน้าที่ดึงข้อมูลจากคิวมาประมวลผลตามลำดับ ขั้นตอนนี้ได้นำเทคโนโลยีปัญญาประดิษฐ์มาใช้งานโดยเชื่อมต่อกับ API ของ Google Gemini AI เพื่อวิเคราะห์บริบทของข้อความ ประเมินความน่าเชื่อถือเบื้องต้น และจำแนกประเภทภัยพิบัติ นอกจากนี้ ระบบได้ประยุกต์ใช้สมการคณิตศาสตร์ฮาเวอร์ไซน์เพื่อคำนวณระยะทางและตรวจสอบการซ้ำซ้อนของข้อมูลโดยมีเงื่อนไขว่า หากมีรายงานใหม่ที่มีพิกัดละติจูดและลองจิจูดอยู่ในรัศมี 500 เมตรจากเหตุการณ์เดิม และมีระยะเวลาห่างกันไม่เกิน 1 ชั่วโมง ระบบจะดำเนินการรวบรวมข้อมูลเข้าเป็นเหตุการณ์เดียวกัน เพื่อลดความซ้ำซ้อน รวมทั้งมีการอ่านข้อมูลเหตุการณ์ภัยพิบัติย้อนหลังมากที่สุด 5 วันเพื่อลดภาระเจ้าหน้าที่ในการตรวจสอบเหตุกาณ์ที่ถูกสร้างซ้ำซ้อนอีกครั้งหนึ่ง
•	กระบวนการจัดเก็บข้อมูล ข้อมูลรายงานที่ผ่านการคัดกรองและวิเคราะห์แล้ว จะถูกบันทึกลงในฐานข้อมูล Amazon DynamoDB ซึ่งเป็นฐานข้อมูลประเภท NoSQL ที่สามารถรองรับการอ่านเขียนข้อมูลที่ไม่มีโครงสร้างตายตัวด้วยความเร็วสูง รวมถึงจัดเก็บประวัติการเปลี่ยนแปลงสถานะอย่างครบถ้วน
•	กระบวนการเชื่อมต่อและส่งต่อเหตุการณ์ ใช้บริการ Amazon EventBridge ในการส่งต่อเหตุการณ์ ทันทีที่รายงานได้รับการตรวจสอบและยืนยันสถานะจากเจ้าหน้าที่ ระบบจะทำการส่งมอบข้อมูลไปยังบริการปลายทางเพื่อดำเนินการเข้าช่วยเหลือต่อไป
ผลการทดสอบและประเมินประสิทธิภาพระบบ
เพื่อยืนยันความถูกต้องและเสถียรภาพของการทำงาน โครงงานนี้ได้ดำเนินการทดสอบระบบตามหลักวิศวกรรมซอฟต์แวร์ โดยแบ่งการประเมินออกเป็น 3 ระดับ ดังนี้
1.	การทดสอบระดับหน่วย (Unit Testing) มุ่งเน้นการทดสอบฟังก์ชันย่อยที่แยกการทำงานอย่างเป็นอิสระ โดยเฉพาะความแม่นยำของโมดูลคำนวณระยะทางฮาเวอร์ไซน์ และโมดูลตรวจสอบความสมบูรณ์ของโครงสร้างข้อมูล จากผลการทดสอบพบว่า ฟังก์ชันทั้งหมดสามารถประมวลผลและให้ผลลัพธ์ที่ถูกต้องแม่นยำ 100% ครอบคลุมกรณีทดสอบในทุกสภาวะ
2.	การทดสอบการทำงานร่วมกัน (Integration Testing) ดำเนินการทดสอบโดยจำลองสภาพแวดล้อมบริการคลาวด์ AWS ผ่านไลบรารี moto เพื่อตรวจสอบการบูรณาการของระบบ ผลการทดสอบพบว่าข้อมูลทั้งหมดถูกนำส่งเข้าสู่คิว Amazon SQS และระบบสามารถสตรีมข้อมูลผ่าน AWS Lambda เพื่อประมวลผล ก่อนจะบันทึกข้อมูลผลลัพธ์ลงในฐานข้อมูล Amazon DynamoDB ได้อย่างครบถ้วน โดยข้อมูล 100% ถูกประมวลผลและส่งต่อระหว่างบริการได้อย่างถูกต้องโดยไม่พบข้อผิดพลาดหรือข้อมูลสูญหายระหว่างทาง 
3.	การทดสอบระบบแบบครบวงจร (End-to-End Testing) ทำการจำลองสถานการณ์เสมือนจริงโดยส่งคำขอความถี่สูงไปยัง API Gateway ผลการทดสอบยืนยันว่า ระบบสามารถทนทานต่อปริมาณข้อมูลที่ส่งเข้ามาพร้อมกัน กระบวนการวิเคราะห์เนื้อหาด้วย AI สามารถทำงานร่วมกับระบบฐานข้อมูลได้อย่างมีประสิทธิภาพ และระบบสามารถจัดกลุ่มรายงานที่อยู่ในพื้นที่และกรอบเวลาเดียวกันได้อย่างถูกต้อง
การวิเคราะห์ผลการดำเนินงาน
จากการประเมินผลเชิงประจักษ์ โครงงานนี้สามารถแก้ปัญหาการจัดการรายงานภัยพิบัติตามที่ระบุไว้ในส่วนที่ 1 ได้อย่างเป็นรูปธรรม การเลือกใช้สถาปัตยกรรมแบบ Serverless เป็นตัวแปรสำคัญที่ช่วยขจัดปัญหาภาวะข้อมูลมหาศาล การใช้คิว SQS เป็นบัฟเฟอร์ข้อมูลช่วยให้ระบบจัดการคำขอที่หลั่งไหลเข้ามาอย่างฉับพลันได้โดยไม่ก่อให้เกิดการล่มของเซิร์ฟเวอร์ นอกจากนี้การนำ Generative AI มาทำงานร่วมกับอัลกอริทึมเชิงพื้นที่ยังเป็นการเพิ่มขีดความสามารถในการทำความสะอาดข้อมูลช่วยลดความซ้ำซ้อนของข้อมูลได้อย่างแม่นยำ การทำงานในลักษณะนี้ช่วยยกระดับความรวดเร็วในการจัดการเหตุฉุกเฉิน และช่วยลดภาระงานของเจ้าหน้าที่ในการคัดกรองข้อมูลดิบจำนวนมากด้วยตนเอง
สรุปผลและข้อเสนอแนะ
โครงงานระบบรับและตรวจสอบรายงานภัยพิบัติแบบ Serverless บรรลุวัตถุประสงค์ที่ตั้งไว้ครบทุกประการ ผลลัพธ์ที่ได้คือระบบต้นแบบที่มีความยืดหยุ่นสูง สามารถจัดเก็บ ประมวลผล และคัดกรองข้อมูลด้วยปัญญาประดิษฐ์ได้อย่างมีประสิทธิภาพ ทางผู้จัดทำมีข้อเสนอแนะสำหรับการพัฒนาต่อยอดในอนาคต คือการขยายขีดความสามารถของระบบโดยบูรณาการเข้ากับระบบแจ้งเตือนแบบเรียลไทม์  เช่น การส่ง SMS กลับไปยังประชาชนในพื้นที่เสี่ยงภัย ตลอดจนการปรับจูนโมเดลปัญญาประดิษฐ์ให้สามารถทำความเข้าใจภาษาถิ่นหรือคำสแลงที่มักใช้รายงานสถานการณ์ในแพลตฟอร์มโซเชียลมีเดีย เพื่อยกระดับความแม่นยำในการคัดกรองข้อมูลขั้นสูงต่อไป
